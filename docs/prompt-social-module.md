# Задача: модуль соцсетей + веб-интерфейс для системы SEO-агентов

## Контекст

Это репозиторий `asilios/seo-agents` — система автоматического SEO для сайтов клиентов на базе Claude Code: оркестратор (`CLAUDE.md`), субагенты в `.claude/agents/` (auditor, keyword-strategist, onpage-optimizer, content-writer, reporter), Python-скрипты, папки клиентов `clients/<client>/` с жизненным циклом правок `changes/pending → approved → applied`, журналом `log.md` и файлом `NEXT.md`. Первый клиент — forma-3d.uz.

Нужно добавить в этот же репозиторий:
1. **Модуль соцсетей** — универсальный, для клиентов из любой ниши (не только 3D-печать), с видео с первой версии.
2. **Веб-интерфейс (dashboard)** — для владельца системы и, позже, для клиентов.

Существующая SEO-часть должна продолжить работать без поломок. Это главный приоритет.

## Фаза 2 — профиль клиента для соцсетей и агенты

### 2.1 Принцип универсальности

Агенты, шаблоны и скрипты — общие для всех клиентов. **В них не должно быть ничего про 3D-печать или конкретную нишу.** Всё отраслевое лежит в `clients/<client>/social/profile.yaml`. Если агенту нужен пример — пример из нескольких разных ниш.

### 2.2 `clients/<client>/social/profile.yaml`

Создай JSON Schema в `core/schemas/social-profile.schema.json` и шаблон профиля. Поля:

- `niche`, `audience` (кто, возраст, боли), `region`, `languages` (например `[ru, uz-Latn]`), `language_mode` (`same_post` | `separate_posts` | `separate_channels`);
- `platforms`: список объектов `{name: telegram|instagram|youtube|tiktok, handle, enabled, autopublish: bool, frequency_per_week, notes}`;
- `pillars` (рубрики): `{id, name, goal, share_percent, formats: [...], example_topics: [...]}`;
- `video_sources`: что клиент может давать — `client_footage`, `catalog_photos`, `screen_recording`, `stock`, `ai_generated` (по умолчанию выключено, платно), `text_slides`; плюс ограничения (например, нельзя лица клиентов);
- `brand`: тон (ссылкой на `client.yaml`, не дублировать), цвета, шрифт, логотип (путь в хранилище), финальная плашка;
- `approval_required`: список типов контента, которые публикуются только после одобрения владельцем (по умолчанию: цены, акции, скидки, сроки и условия доставки, гарантии, обещания, отзывы с именами, упоминание конкурентов);
- `utm`: шаблон меток;
- `hashtags`: базовые по площадкам;
- `forbidden`: темы и слова.

Общие данные клиента (контакты, доставка, тон, запреты бренда) не дублировать — брать из `client.yaml`.

### 2.3 Агенты (`.claude/agents/`)

Каждый агент: чёткая роль, входы, выходы (пути файлов), что ему запрещено, формат результата. Факты — только из сайта клиента, каталога, статей, `client.yaml` и данных; нет данных — так и пишется.

**`social-strategist`** — стратег.
- Когда: при подключении клиента, затем раз в месяц.
- Изучает нишу, аудиторию и 3–5 конкурентов в соцсетях (через Firecrawl), читает SEO-ядро и сайт.
- Предлагает площадки, частоту, рубрики, микс форматов, источники видео.
- Раз в месяц пересматривает стратегию по метрикам от reporter.
- Выход: `social/strategy.md`, черновик `profile.yaml` → владельцу на подтверждение.

**`social-planner`** — планировщик.
- Когда: каждую неделю.
- Составляет план постов на неделю по рубрикам и долям из профиля. Темы: SEO-ядро (`seo/keywords/`), статьи базы знаний, каталог, сезонность и праздники региона, результаты прошлых недель.
- Каждый пост: id, площадки, дата и время, рубрика, формат ролика, целевая страница сайта, источник видео.
- Проверяет, хватает ли исходников; если нет — формирует список съёмки.
- Выход: `social/plan/<YYYY-Www>.md`, `social/shotlist/<YYYY-Www>.md`.

**`social-writer`** — копирайтер и сценарист.
- Пишет тексты под каждую площадку и язык (учитывать лимиты длины, стиль площадки).
- Пишет сценарий ролика: раскадровка по секундам, текст на экране, субтитры по языкам, призыв в конце.
- Ссылки с UTM, хэштеги.
- Помечает пост флагом `needs_approval`, если в нём есть что-то из `approval_required`.
- Выход: `social/pending/<post-id>/post.md` (frontmatter + тексты) и `script.json` (машиночитаемый сценарий для монтажа).

**`video-editor`** — монтажёр.
- Подбирает исходники по сценарию из хранилища клиента (или стока).
- Собирает ролик по шаблону через Remotion: 9:16, 15–60 с, субтитры, надписи, музыка из лицензированной бесплатной библиотеки (источник и лицензию записывать в пост), финальная плашка с брендом.
- Делает обложку.
- Самопроверка: длительность, есть звук/или осознанно без звука, текст читаемый и в безопасных зонах интерфейса площадок, нет чужих логотипов и водяных знаков, нет лиц без отметки о согласии.
- Выход: файлы в хранилище, ссылки — в `post.md`.

**`reporter`** (существующий) — расширить, не создавать новый.
- Добавить раздел «Соцсети»: просмотры, охват, подписчики по площадкам; переходы по UTM; динамика брендовых запросов в GSC; лучшие и худшие рубрики/форматы.
- Вывод «что работает» сохранять в `social/insights.md` — его читают strategist и planner.

**Не агент, а скрипты:**
- `modules/social/publishers/` — по одному модулю на площадку с единым интерфейсом: `publish(post, platform) -> {url, platform_post_id}`;
- `modules/social/checks/` — проверки перед публикацией (см. ниже).

### 2.4 Жизненный цикл поста

```
social/pending/<post-id>/  → social/approved/<post-id>/ → social/applied/<post-id>/
                                                       ↘ social/failed/<post-id>/  (с причиной)
```

- Посты без `needs_approval`, прошедшие проверки, переходят в `approved/` автоматически.
- Посты с `needs_approval` ждут владельца (команда `/social-approve` или кнопка в интерфейсе).
- `post.md` хранит статус, историю переходов, ссылки на опубликованные посты.
- Журнал: `social/log.md`.

### 2.5 Проверки перед публикацией (`modules/social/checks/`)

- целевая ссылка отдаёт 200 (и UTM на месте);
- длина текста в пределах лимита площадки;
- язык соответствует версии (нет кириллицы в `uz-Latn`, и т. п.);
- нет незаполненных заглушек (`{{`, `TODO`, `lorem`);
- цены и акции совпадают с сайтом и одобрены;
- видео: формат, разрешение, длительность и размер в пределах требований площадки;
- лимит частоты на площадку (не больше N постов в день из профиля).

Проверка не прошла → пост в `failed/` с причиной, владельцу — уведомление в отчёте.

### 2.6 Команды (`.claude/commands/`)

- `/social-setup <client>` — анкета + запуск strategist, создание `profile.yaml`;
- `/social-weekly <client>` — planner → writer → video-editor → проверки → публикация одобренного;
- `/social-approve <client> [post-id]` — показать очередь одобрения, одобрить/отклонить/вернуть на доработку с комментарием;
- `/social-monthly <client>` — пересмотр стратегии;
- обновить `/new-client`, чтобы предлагал подключить соцсети.

## Фаза 3 — видео

- Шаблоны на **Remotion** в `modules/social/templates/` (отдельный package.json). Шаблоны принимают `script.json` и `brand` и не содержат ничего про конкретную нишу.
- Базовые форматы для первой версии:
  1. `process` — процесс/таймлапс с подписями;
  2. `qa` — вопрос → ответ (тема из SEO-ядра);
  3. `showcase` — витрина товара/услуги из фото;
  4. `text-slides` — текст на фоне, минимальный вариант.
  Позже: `before-after`, `testimonial`, `behind-the-scenes`.
- Субтитры — из сценария (не распознавание речи) на первой версии.
- Озвучку голосом не делать в первой версии.
- Стоковое видео: адаптер под бесплатный API (например Pexels), с записью источника и лицензии.
- ИИ-генерация видео: только интерфейс-заглушка и флаг в профиле, без реализации.
- Хранилище файлов: **Cloudflare R2** (S3-совместимое). Структура: `<client>/raw/`, `<client>/rendered/`, `<client>/brand/`. В git видео не попадают — добавь в `.gitignore`.
- Рендер локально (для отладки) и в GitHub Actions.

## Фаза 5 — интерфейс (`dashboard/`)

Стек: **Next.js (App Router) + TypeScript + Tailwind**, деплой на **Railway**. Источник данных в первой версии — файлы репозитория через **GitHub API** (без отдельной БД); медиа — из R2 по подписанным ссылкам.

### Роли
- `admin` (я) — всё;
- `client` (позже) — только свой клиент: очередь одобрения, загрузка исходников, отчёты.
Авторизация: простая — email + пароль или magic link (предложи вариант). Сессии на сервере.

### Экраны
1. **Клиенты** — список: домен, подключённые модули, статус последнего цикла SEO и соцсетей, сколько ждёт одобрения.
2. **Обзор клиента** — ключевые метрики SEO (показы, клики, позиции главных запросов против baseline) и соцсетей (просмотры, переходы по UTM), открытые вопросы из `NEXT.md`.
3. **Очередь одобрения** — общая для SEO-правок и постов: превью (текст, видео-плеер, diff правки на сайте), кнопки «Одобрить», «Отклонить», «Вернуть с комментарием». Действие = коммит через GitHub API, перенос файла и запись в журнал.
4. **Контент-календарь** — посты по дням и площадкам, статусы (`pending/approved/applied/failed`), фильтры по рубрике и площадке.
5. **Пост** — тексты по площадкам и языкам, сценарий, видео, обложка, история статусов, ссылки на опубликованное.
6. **Исходники** — загрузка видео и фото в R2 (большие файлы — прямой загрузкой по подписанной ссылке), текущий список съёмки (`shotlist`) с отметками «снято».
7. **Отчёты** — список отчётов из `reports/`, рендер markdown.
8. **Журнал** — `log.md` модулей с фильтром.
9. **Настройки клиента** — просмотр `client.yaml` и `social/profile.yaml`; редактирование через форму с валидацией по JSON Schema (сохранение = коммит).

### Требования
- Интерфейс не пишет напрямую в `applied/` и не публикует сам — только меняет статусы; публикуют Actions.
- Каждое действие в интерфейсе пишется в журнал клиента: кто, что, когда.
- Мобильная версия обязательна (одобрять буду с телефона).
- Язык интерфейса — русский, тексты вынести в один файл, чтобы позже добавить узбекский.
- Кэширование ответов GitHub API, чтобы не упираться в лимиты.

## Общие правила работы

- Работай по фазам. После каждой фазы: краткий итог, что сделано, что проверено, что осталось, и **остановись** до моего подтверждения.
- Каждая фаза — отдельная ветка и отдельные осмысленные коммиты; в `main` — после моего «ок».
- Не ломай SEO-модуль. После любых изменений в общих файлах — прогон SEO в сухом режиме.
- Никаких выдуманных фактов, цифр, отзывов, цен — ни в агентах, ни в тестовых данных для реальных клиентов.
- Никаких секретов в коде и коммитах.
- Если для решения нужен мой выбор (тариф API, сервис авторизации, что-то платное, необратимое действие) — спрашивай, не решай сам.
- Обнови `NEXT.md` и документацию (`docs/system-overview.md` — создай, если нет) в конце каждой фазы, чтобы следующий запуск мог продолжить с того же места.
