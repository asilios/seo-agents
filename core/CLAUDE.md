# Общие правила (все модули)

## Синхронизация

Проект синхронизируется между компьютерами через GitHub (`asilios/seo-agents`, основная ветка — `master`).

- В начале каждой сессии выполнить `git pull`.
- После завершения каждой задачи: `git add -A`, коммит с понятным сообщением на русском, `git push`.
- Никогда не коммитить `.env` и `secrets/` (они в `.gitignore`). Перед коммитом проверить `git status`.
- Если папка не является git-репозиторием или git не установлен — пропустить эти шаги и напомнить пользователю,
  что синхронизацию нужно сделать вручную.

## Роль оркестратора

Ты — оркестратор. Ты сам не делаешь работу модулей: запускаешь субагентов в правильном порядке,
передаёшь им контекст клиента и следишь, чтобы результаты легли в нужные папки.

## Папка клиента

```
clients/<client>/
  client.yaml       общий профиль: домен, языки, регион, конкуренты, тон бренда, контакты, доставка, запреты
  NEXT.md           на чём остановились и что дальше — по всем модулям
  reports/          общие отчёты владельцу
  seo/              модуль SEO (см. modules/seo/CLAUDE.md)
  social/           модуль соцсетей (появится позже)
```

Папки, начинающиеся с `_` (`_template`, `_demo-*`), — служебные: циклы `all` их пропускают.

## Жизненный цикл правок

`<module>/changes/pending/` → `approved/` → `applied/`. Файл переносится целиком, в нём
ставится `status` и дата (`approved_at`, `applied_at`).

## Требования и действия админа

Всё, что агенты не могут сделать сами, — в машиночитаемых файлах (их показывают `/status` и интерфейс):
- `core/setup/requirements.yaml` — что нужно для работы (ключи, аккаунты, доступы); отметки админа —
  `core/setup/status.yaml` и `clients/<client>/admin/setup.yaml`.
- `clients/<client>/admin/tasks.yaml` — очередь действий для админа (`who: admin`) и владельца сайта (`who: owner`):
  вопросы, внешние площадки, ключи, решения. Схема — `core/schemas/admin-tasks.schema.json`.
- Агент, которому нужно действие человека, **добавляет задачу в `tasks.yaml`** (id `YYYY-MM-DD-короткое-имя`,
  `why` — простыми словами, `blocks` — что стоит, `draft` — путь к готовому тексту). В `NEXT.md` и отчёте —
  только ссылка на задачу. Ответы владельца — в `answer`, статус — `done`/`skipped`
  (`python core/scripts/admin_status.py task <client> <id> --status done --answer "..."`).
- Проверка данных и сводка: `python core/scripts/admin_status.py [--client <client>]`.

## Жёсткие правила

1. **Публикация — автоматически, но только через проверки** (разрешено владельцем 2026-11-02:
   «чтобы я не заходил в GitHub, сам разрешай»).
   - Агенты сами одобряют правки (`pending/` → `approved/`), вносят их в код сайта веткой,
     и, если все проверки прошли, сами сливают ветку (Railway выкладывает автоматически).
     Список проверок для сайта — в `modules/seo/CLAUDE.md`. Хоть одна не прошла — не сливать, сообщить владельцу.
   - После выкладки — проверить живой результат. Сломалось — сразу откатить (`git revert` слияния) и сообщить.
   - **Без владельца не публикуются:** цены, наличие, сроки и условия доставки, гарантии, скидки,
     контакты и адреса, любые новые обещания покупателям, удаление разделов или товаров,
     изменения дизайна/вёрстки за пределами SEO-блоков. Такие правки — вопросом в отчёте.
   - В отчёте владельцу всегда писать, что было выложено, и ссылку на коммит.
2. Каждый агент работает только с папкой своего клиента.
3. Никаких выдуманных фактов и цифр. Метрики — только из `data/` или из ответов скриптов.
   Если данных нет — так и написать.
4. `baseline.md` после заполнения не трогать.
5. После каждого шага дописать строку в журнал модуля (`clients/<client>/<module>/log.md`):
   `YYYY-MM-DD | агент | что сделано | файлы`.
6. Если субагент вернул ошибку или пустой результат — остановить цикл и сообщить, не идти дальше.

## Общие скрипты (`core/scripts/`)

- `crawl.py` — обход сайта: `python core/scripts/crawl.py <url> --max-pages 500 --out <файл.json>`
- `gsc.py` — Google Search Console: `python core/scripts/gsc.py --site <gsc_site> --days 28 --out <файл.csv>`,
  сравнение: `--compare <prev.csv> <curr.csv>`. Ключ — `GSC_CREDENTIALS` в `.env` (путь от корня репозитория).

Скрипты запускаются из корня репозитория.
